# 编辑器撤销与重做规范

状态：项目级强制规范  
适用范围：Story Blueprint Editor 中所有会改变项目内容的作者操作

## 1. 目标

用户应当可以放心尝试编辑操作。只要操作改变了 Story、Graph、项目资源或资源属性，就必须能够通过 Undo 恢复操作前的完整状态，并能够通过 Redo 再次应用。

本规范中的“必须”“不得”是实现要求，不是建议。

## 2. 核心原则

1. **所有内容修改必须可撤销。** 新增、删除、复制、移动、排序、连接、断开、重命名、修改属性、批量处理和自动处理都必须进入统一编辑历史。
2. **新增与删除必须对称恢复。** Undo 删除必须恢复原对象；Undo 新增必须完整移除新增对象。Redo 必须重新得到相同的语义结果。
3. **恢复的是完整状态，不只是界面。** 对象本身、稳定 ID、顺序、父子关系、引用、连线、资源路径映射和相关属性必须一起恢复。
4. **一次用户意图对应一个历史步骤。** 一个按钮、一次拖放、一次确认或一次批量命令产生一个 Undo 检查点，不得要求用户连续撤销内部实现步骤。
5. **历史不能产生非法中间态。** 具有依赖关系的修改必须作为原子事务提交、撤销和重做。
6. **持久化位置不改变规则。** 数据位于当前 Story、Substory、`.storyproject`、独立资源文件或内存暂存区，都必须遵守相同的撤销语义。

## 3. 必须覆盖的操作

以下列表不是穷举。任何新增的作者操作，只要会改变项目内容，默认都属于可撤销操作。

### 3.1 Graph 与节点

- 新增、删除、复制和粘贴节点。
- 移动节点、批量移动和自动布局。
- 新增、删除、替换、转移和重新路由连线。
- 新增、删除和移动 Reroute、Comment、Flow Portal。
- 新增、删除、拆分、合并和排序 Dialogue Line、Choice Option。
- 修改节点属性、表达式、Ink 内容以及动态端口。
- 创建子故事、从选中节点提取子故事和跨 Graph 的原子编辑。

### 3.2 项目资源

- 新增和删除 Story、Substory、Character、Variable、Asset、Event、Signal 及后续扩展资源。
- 新增和删除 Character Field、Emotion、Relationship、Metadata、Tag 等子项。
- 修改资源名称、显示名、描述、默认值、类型、资源引用和自定义字段。
- 文件夹内移动、排序或重新归属资源。

删除项目资源时，Undo 必须恢复资源内容、原相对路径、项目索引登记和所有由同一事务修改的引用。若底层无法可靠恢复，功能不得伪装成普通可撤销删除，必须在执行前明确标记为不可撤销并二次确认；项目内的常规删除不应采用这种例外。

### 3.3 自动化与批量操作

- AI Command Apply、Story Merge Apply、批量重命名、引用改写和格式迁移。
- 自动布局、自动修复、批量导入和批量删除。
- 一次批量操作无论内部修改多少对象，默认只产生一个历史步骤。

## 4. 原子事务边界

下列关联修改必须共享同一个历史步骤：

- 删除节点与删除其所有关联连线。
- 删除 Choice Option 与删除其动态输出连线。
- Character Emotion 改名或删除与所有 Dialogue 引用改写。
- Variable 或 Character Field 改名与所有表达式、模板和节点引用改写。
- 删除资源与项目索引、文件和引用的同步更新。
- Dialogue 合并、拆分与边界连线重写。
- AI 或 Merge 的整次 Apply。

Undo 后必须直接回到事务开始前的合法状态；Redo 后必须直接回到事务完成后的合法状态。不得向历史中暴露“对象已经删除但引用还在”等内部阶段。

## 5. 文本和连续交互

- 普通文本框应使用本地草稿。输入过程中保留控件自身的文字撤销；失焦、Enter 或明确提交时，将最终差异作为一个编辑器历史步骤提交。
- Monaco 等代码编辑器在聚焦时优先处理其内部 Undo / Redo。内容应用到 Story 后，整次应用还必须成为一个编辑器历史步骤。
- 拖动节点或资源时，可以持续预览；在拖动结束后只记录一个历史步骤。
- 数值微调、滑块和连续按键应按一次连续交互合并，避免每一帧或每一个字符污染历史。
- 没有产生语义变化的提交不得创建空历史步骤。

## 6. 外部资源与磁盘同步

- Undo / Redo 首先恢复统一的编辑器状态，再按队列将最终状态写回对应文件。
- 独立资源文件的恢复必须同步更新 Workspace 内存、项目索引和磁盘内容。
- 写入失败时必须保留可复制的错误信息，并明确显示内存状态与磁盘状态不一致；不得静默丢弃历史或覆盖较新的外部修改。
- 连续执行 Undo、Redo 时，磁盘写入必须保持顺序，最终磁盘内容必须与当前历史位置一致。
- Save 不是历史步骤。保存只持久化当前状态，不得清空 Undo / Redo；只有打开另一项目、明确重载或用户确认丢弃时才可以重置历史。

## 7. 快捷键与界面

- Undo：`Ctrl+Z`；Redo：`Ctrl+Y` 和 `Ctrl+Shift+Z`。
- Edit 菜单必须提供同等操作，并根据当前历史状态启用或禁用。
- Inspector、Graph、资源管理器和浮动面板必须接入同一编辑历史。
- 当普通表单已结束一次新增或删除操作后，即使焦点仍在 Inspector，快捷键也必须能撤销该操作。
- 输入控件内部仍有未提交的文字编辑时，快捷键优先作用于文字；提交后作用于编辑器事务。
- 执行新修改后必须清除当前历史位置之后的 Redo 分支。

## 8. 不进入内容历史的操作

以下操作默认不进入项目内容的 Undo / Redo：

- 选择节点、框选、画布平移和缩放。
- 打开或关闭面板、调整 Dock 布局。
- 搜索、预览导航和仅查看 Inspector。
- 尚未 Apply 的 AI Proposal、Merge Preview 或其他暂存预览。
- Save、Build、Compile、运行预览以及 Git 状态查询。

如果这些操作最终修改项目内容，例如将预览 Apply、保存面板布局到项目配置或接受自动修复，则修改部分仍必须进入历史。

## 9. 明确不属于编辑器 Undo 的外部操作

Git Commit、切换分支、发布仓库、删除项目目录等外部系统操作不使用编辑器内容历史。它们必须使用各自的恢复机制和风险确认，且不得与普通的项目内资源删除使用相同的无提示交互。

## 10. 实现要求

- 历史记录应保存足以恢复语义状态的数据，不依赖当前 UI 组件是否仍挂载。
- 稳定 ID 在删除后 Undo 时必须恢复原值；Redo 不得生成新的身份。
- 历史事务必须覆盖所有受影响的 Graph、Chapter、项目资源和引用，不能只保存当前活动 Graph。
- 内存对象与历史快照之间不得共享可变引用。
- 异步写盘不能反向覆盖更新的历史状态。
- 历史容量达到上限时只淘汰最旧的完整事务，不得拆分事务。

## 11. 验收清单

每个新增或修改内容的功能在合并前必须验证：

1. 操作一次后，按一次 Undo 是否完整恢复。
2. 再按一次 Redo 是否完整重现。
3. 对新增、删除、重命名、排序和引用修改是否分别成立。
4. 是否保留稳定 ID、连线、顺序、父级和资源相对路径。
5. 是否同时恢复内存、Workspace、项目索引和磁盘文件。
6. 操作是否只产生符合用户意图数量的历史步骤。
7. Undo 后进行新编辑，旧 Redo 是否正确失效。
8. 写盘失败或外部文件变化时，是否阻止静默覆盖并给出可复制错误。
9. 从 Inspector、菜单和快捷键触发时行为是否一致。
10. 自动化测试是否至少覆盖操作、Undo、Redo 和重新序列化后的结果。

## 12. 新功能默认规则

设计评审和代码评审应默认询问：**“这个修改如何 Undo 和 Redo？”**

若功能设计没有答案，则该功能尚未完成。新增内容操作不得以“以后再补撤销”为完成状态。
